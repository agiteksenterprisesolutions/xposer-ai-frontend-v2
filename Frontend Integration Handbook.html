01Three breaking changes

Start here. Each one silently breaks working code rather than throwing, which is why they are first.

1 · Roles are no longer a fixed enum

There used to be five role codes. Now an organization defines as many as it wants, names them what it wants, and grants each whatever permissions it wants. Only two codes are structural and uneditable: admin (the root role) and reporter (the public self-service identity). manager, officer and reviewer still exist, but only as a starting point every new organization is seeded with — they can be renamed, re-permissioned or deleted.

What breaks

Any role === 'admin', ['manager','officer'].includes(role), hardcoded role dropdown, or role-keyed lookup table. These now return the wrong answer for any organization that has customised its roles — and they fail quietly, showing a user too little UI or too much.

What to do

Never branch on role identity. Branch on a permission from GET /users/me → permissions[]. Populate every role dropdown from GET /xp/org-roles/. See §02.

2 · Report types store English only

Every translation field is gone from the API. Translations are now a frontend concern, which is the right side of the boundary: the database holds one canonical English definition, and the app renders it in whatever language the reporter picked.

RemovedWasNow
*_i18n on every text field{"en": "...", "ar": "..."}gone — the plain field is English
Option.labela LocalizedText objecta plain string
locales, locale_directionsdeclared per report typegone
is_rtl, text_directionserver-computedgone — derive from the UI locale
What breaks

Any reader of question.label_i18n[locale] or option.label.en. The first throws on undefined; the second returns undefined and renders an empty option — a silent, shipped bug.

What to do

Read the plain field, and look up a translation in your own i18n bundle keyed on stable identifiers — reportType.code, section.section_key, question.name, option.value — never on the English text, which changes when someone edits a typo.

Suggested key scheme
// value, not label: the label is display text and will be edited
t(`rt.${reportType.code}.name`, { defaultValue: reportType.name })
t(`rt.${reportType.code}.s.${section.section_key}.title`, { defaultValue: section.title })
t(`rt.${reportType.code}.q.${question.name}.label`, { defaultValue: question.label })
t(`rt.${reportType.code}.q.${question.name}.o.${option.value}`, { defaultValue: option.label })
Open question for you to decide

Nothing now records the question text a reporter actually saw at submission. Previously the stored translations were an implicit audit trail. If the compliance team needs "what exactly was this person asked", the answer has to be snapshotted onto the report at submit time — either client-side into the payload, or as a backend change. Flag it; it is not built.

02The permission gate

One pattern replaces every role check. The server resolves permissions from the organization's own role document on every request, so they are never stale and never in the token.

GET/xp/users/me— any authenticated user
Response (abridged)
{
  "id": "66f1...",
  "email": "lead@acme.com",
  "role": "finance_lead",          // a code, not an enum member
  "organization_id": "66f0...",
  "permissions": ["report:read_all", "report:manage", "agent:summary_read", ...]
}
The only access helper you need
export const PERM = {
  reportReadAll:    'report:read_all',
  reportManage:     'report:manage',
  roleManage:       'role:manage',
  agentRead:        'agent:read',
  agentManage:      'agent:manage',
  agentSummaryRead: 'agent:summary_read',
  hierarchyRead:    'org_hierarchy:read',
  hierarchyManage:  'org_hierarchy:manage',
  // …the full list is in §12
} as const;

export function useCan() {
  const { permissions } = useCurrentUser();
  const held = useMemo(() => new Set(permissions ?? []), [permissions]);
  return useCallback((...needed: string[]) => needed.every(p => held.has(p)), [held]);
}

// usage — note it gates on capability, never on who someone is
const can = useCan();
{can(PERM.agentManage) && <Button>New agent</Button>}
Refetch /users/me after a role edit

The server resolves per request, so a permission change takes effect on the next call with no re-login. But your cached permissions array does not know that. Invalidate the users/me query after any successful write to /org-roles/, and after changing the role on the signed-in user.

Hide, but also handle the 403

Hiding a button is a courtesy, not a control. Every one of these endpoints enforces server-side, so a deep link or a stale tab will produce a 403 — render a "you no longer have access to this" state rather than an error toast on a blank screen.

Two headers the browser app never sends

X-Agent-Key (an AI agent acting on a report) and X-Service-Key (server-to-server, the multiagent runtime bundle) exist in the API but are not for a browser client. If you find yourself needing either from the frontend, something is wrong with the design — say so rather than working around it.

03Error contract

Four shapes. The 400 is new and carries structured, user-presentable problems — build one handler that understands it and every screen below gets good errors for free.

StatusMeaningdetail shape
422Schema validation, before any logic — missing field, number out of bounds, bad enum[{loc, msg, type}]
400A business rule. New shape.{message, problems[], warnings?}
403Missing permission, or granting one you don't holdstring
409A guard — duplicate code, fixed role, still in usestring
One normaliser for all four
type Problem = { code?: string; message: string; permission?: string;
                  requires?: string[]; row?: number; field?: string;
                  stage?: string; capability?: string };

export function normaliseError(status: number, body: any):
    { summary: string; problems: Problem[] } {
  const d = body?.detail;

  // 400 from a business rule — the useful case
  if (d && typeof d === 'object' && !Array.isArray(d) && d.message) {
    return { summary: d.message, problems: d.problems ?? [] };
  }
  // 422 from Pydantic
  if (Array.isArray(d)) {
    return {
      summary: 'Some fields need fixing.',
      problems: d.map((e: any) => ({
        field: e.loc?.filter((x: any) => x !== 'body').join('.'),
        message: e.msg,
      })),
    };
  }
  // 403 / 409 / anything else
  return { summary: typeof d === 'string' ? d : 'Something went wrong.', problems: [] };
}
The messages are written for users

Every problems[].message from the new rules is a complete sentence aimed at whoever is looking at the screen — "'report:manage' needs 'report:read_all' or 'report:read_assigned' as well — without one of those, this role can never open the reports it would be acting on." Render them verbatim; do not re-word them into "Invalid input".

Building the checkbox tree

GET /xp/org-roles/permissions

  • Render one collapsible section per group, using label as the heading.
  • Disable any checkbox where granted is false — the caller cannot grant a permission they do not hold, and the save would 403. Show a tooltip saying so.
  • requires_any_of means at least one of, never all of. Use it to auto-tick or to warn inline.
  • The four platform-only permissions are absent from the catalog entirely. Do not hardcode them into a picker.

Live validation

Two layers. Do the cheap one locally from dependencies so ticking a box gives instant feedback, and call the endpoint on a debounce so the messages you show are the exact ones the save would produce.

The role list, and the fixed roles

  • is_fixed: true → render read-only. Edit and delete both return 409. Its id is the literal string "admin", so do not treat ids here as ObjectIds.
  • is_system_default: true with no is_fixed means seeded-but-editable (manager, officer, reviewer). Fully editable — a badge, not a lock.
  • reporter is not in this list at all. It is the public self-service identity, not something an organization manages. Do not offer it in a staff role picker.
  • A successful create or update returns the role with a warnings array attached. Surface it as a post-save toast rather than discarding it.
Two 409s to handle on delete

"N active user(s) still have this role — reassign them first" → offer a link to the filtered user list. "This is the only role that can manage roles…" → explain rather than retry.

Assigning a role to a user

POST/xp/users/— user:create
PUT/xp/users/{user_id}— user:update (+ user:manage_roles to change `role`)

role is simply a role code. Populate the dropdown from GET /xp/org-roles/, excluding nothing except what your product rules say — every listed code is assignable.

  "effective_permissions": ["report:read_all", ...],

  "disabled_capabilities": [
    { "capability": "message_reporter", "requires": "message:create" }

effective vs ticked — the key UI idea

capabilities is what someone ticked. effective_capabilities is what will actually happen, after intersecting with the permissions the agent's role carries. disabled_capabilities explains the difference. Show a ticked-but-disabled capability with a warning icon and the sentence "needs message:create on the finance_lead role" — and a link to that role. Without this an admin cannot tell why their agent is silent.

This is resolved live, so revoking a permission on the role moves a capability into disabled_capabilities on the very next read, with no edit to the agent. Refetch agents after any role write.

06Summarizer settings

A small screen with one subtlety worth getting right. The summarizer is an ordinary agent, but whether it runs is an organization-level switch — separate from its role, its is_active flag, and the workflow.

GET/xp/org-agents/summarizer— agent:read
PUT/xp/org-agents/summarizer— agent:manage
GET response
{
  "enabled": true,               // what the org asked for
  "agent_code": null,             // explicit choice; null = infer
  "include_attachments": true,
  "max_words": 400,                // 50–4000

  "active": true,                // ← what will ACTUALLY happen
  "resolved_agent": {
    "code": "summarizer", "name": "Summarizer", "is_active": true,
    "role_code": "officer", "role_source": "org_role",
    "effective_capabilities": ["read_attachments"],
    "disabled_capabilities": []
  },
  "available_agents": [{ "code": "summarizer", "name": "Summarizer", "is_active": true }],
  "affected_stages": ["summarize"],   // which workflow stages this switch controls
  "problems": [],
  "access": {
    "permission": "agent:summary_read",
    "granted_to":     [{ "code": "admin", "name": "Admin", "is_fixed": true }, ...],
    "not_granted_to": [{ "code": "poster", "name": "Poster", "is_fixed": false }],
    "how_to_change": "Grant or revoke agent:summary_read on the role…"
  }
}
Render `active`, not `enabled`

The toggle's bound value is enabled; the status line beside it must read active. When they disagree, show every problems[].message — the switch is on but nothing will happen, and the reason is one of:

  • no_summarizer_agent — none exists. Offer "Create a summarizer".
  • ambiguous_summarizer — several exist and none chosen. Show the available_agents picker; the backend deliberately refuses to guess.
  • summarizer_inactive — the chosen agent is deactivated. Link to it.
  • cannot_read_attachments — evidence parsing is on but the agent's role lacks report:read_all. Advisory: it will digest report text only.
Show `affected_stages` next to the toggle

So the consequence of switching it off is visible before it is switched off. Turning it off does not edit the workflow, deactivate the agent, or touch any role — say so in the helper text, because that is what makes it safe to flip back on.

`access` is a read-only mirror, not an editor

There is no second sharing list to manage here. agent:summary_read on a role is the access control. Render granted_to / not_granted_to as chips with a link into the roles editor, and do not build a save action on this block — a fixed role among them cannot be changed at all.

PUT body — all fields optional
{ "enabled": false }
{ "enabled": true, "agent_code": "digest", "max_words": 250, "include_attachments": false }

max_words outside 50–4000 is a 422. An agent_code that is not a summarizer-kind agent, or does not exist, is a 400 with a plain string.

07Workflow builder

An ordered list of stages. Each names an executor — one of the organization's agents, or one of its human roles — and optionally where to go for each verdict.

GET /xp/org-workflows/List. agent:read
GET /xp/org-workflows/activeThe one a report submitted now would run. agent:read
POST /xp/org-workflows/validateDry-run. Saves nothing. agent:read
POST /xp/org-workflows/Create. agent:manage
PUT /xp/org-workflows/{id}Update. agent:manage
DELETE /xp/org-workflows/{id}Delete. agent:manage
Stage shape
{
  "key": "triage",                 // slug: [a-z0-9_] only
  "name": "Triage",
  "executor_type": "agent",        // "agent" | "human"
  "executor_ref": "manager",        // agent code, or role code when human
  "transitions": [
    { "when_decision": "ask_info", "goto": "end" },
    { "when_decision": "assign",   "goto": "next" }
  ],
  "optional": false                 // MAY BE ABSENT — default it to false
}
  • goto is another stage's key, or the reserved "next" / "end". A stage with no rule for the verdict it returned falls through to next, so only interesting branches need writing down.
  • when_decision must be one of the executing agent's decisions. Populate that dropdown from the selected agent, not from free text.
  • A human stage pauses the run for the dashboard. "Fully automated" and "fully human" are no longer modes — they are just which executor each stage has.
  • Backward jumps are allowed (review → investigate). Termination is bounded by max_stage_visits (1–20, default 3), so do not reject a cycle in the builder.
  • optional may be missing from stored stages — treat undefined as false.
Always call /validate before /create

It returns [{code, stage, message}], so you can pin each problem to the stage card that caused it. It catches a goto to a stage that does not exist, an executor_ref that does not exist, a when_decision the agent never returns, a transition on a summarizer-kind stage, and duplicate keys.

Two 409s

Deleting the only workflow is refused — an organization with none has nothing to run. And deleting an agent still referenced by a stage is refused, so the builder is where a user must go first.

Read the effective fields; show the override as provenance

level_code and manager_external_id already carry the answer — the manual correction where one was made, the synced value otherwise. The *_from_hr fields exist so you can render "overridden from (none)" beside an entry. Never compute the effective value yourself.

has_manual_override is only true for an hr_sync entry a human has corrected — a purely manual person has nothing to override, so use source for the "added by hand" badge and has_manual_override for the "corrected" badge.

Two provenance badges, and what each implies
  • source: "manual" — added by hand. Survives every sync untouched. Deleting removes it outright.
  • source: "hr_sync" — HR owns it. Absent from the next pull, it is deactivated automatically. Deleting only deactivates it, because a real delete would be undone by the next sync — say that in the confirm dialog.

A manual entry that HR later starts reporting flips to hr_sync and keeps its overrides. Worth a tooltip, because the badge will appear to change on its own.

  • row is 1-indexed against the array you sent — map it straight onto the row in your paste grid and highlight the named field.
  • Always run dry_run=true first and show a preview. {"would_create": N, "external_ids": [...]} comes back and nothing is written.
  • Managers may reference other rows in the same upload, in either direction — do not validate manager references client-side against only what is already on the server.
  • It is genuinely all-or-nothing, so a single bad row leaves the directory untouched. Say so in the error panel; a user who has pasted 300 rows needs to know they have not half-loaded.

Make Preview the primary action, Sync the secondary one

POST /sync/preview writes nothing and returns records_returned, would_upsert, would_skip_missing_id_or_name, unmapped_designations, field_mapping_used and a sample of mapped rows. A field mapping is guesswork until it meets the real payload, and POST /sync writes over the live directory.

Surface would_skip_missing_id_or_name prominently: non-zero almost always means the mapping points at the wrong key for external_id or name. The real sync drops those rows silently, so a wholly wrong mapping otherwise looks like a successful sync of nobody.

  • credential comes back as •••••••• on every read. Treat the field as write-only: an empty input means "leave unchanged", which is what PATCH is for.
  • POST /sync returns {synced, matched_to_a_level, unmatched_designations[], deactivated, synced_at}. Show unmatched_designations as the follow-up task — each is a job title to add to a level's aliases.
  • An unreachable or non-JSON HR API is a 502 with the reason, and nothing already synced is touched. Render it as "could not reach your HR system", not a generic failure.

Never render `matched: false` as "nobody is implicated"

It means the directory could not identify anyone named in the text, so a human decides. Matching is exact, case-insensitive and whole-word by design — no fuzzy matching — because a near miss must not resolve in a system that decides who gets told about an allegation against them. matched: true with escalate_to_member: null is a third state: someone was identified but there is no one above them on file. All three need distinct copy.

A "test this report's routing" panel on the report detail screen is the natural home for this.

Two different screens, two different permissions

The full run carries every agent's prompts, verdicts and reasoning — an audit view for whoever administers the agents (agent:read). The digest is the factual summary of the evidence on one case, useful to whoever is working that case (agent:summary_read). Put the digest on the report detail screen and the full run under agent administration. Do not gate the digest panel on agent:read, or you reintroduce exactly the over-granting this split removed.

11Report types

Beyond the i18n removal in §01, the import/export workbook changed and there is one behaviour you must design around.

GET /xp/report-types/export?active_only=. xlsx. report_type:manage
GET /xp/report-types/import/templateBlank workbook. report_type:manage
POST /xp/report-types/importmultipart file. report_type:manage
  • Both GETs return a binary .xlsx. Read the filename from Content-Disposition; do not construct it.
  • The workbook has 8 sheets and 50 English columns in 6 colour-coded bands. No Arabic columns.
  • An older workbook that still has AR columns imports fine — they come back as header.unknown_column warnings. Show warnings distinctly from errors: the import succeeded.
  • Export → edit → re-import round-trips losslessly (verified at 72 types / 2018 questions).
Import does not upsert — design for this

It matches on report type name, not on Report Type Code. Importing the same file twice fails with one "a report type named 'X' already exists" problem per type. There is no dryRun parameter and no version history.

Consequences for the UI: do not offer "re-import to update"; label the action Import new report types. Import is all-or-nothing and returns every problem at once, so you can implement a client-side dry run by uploading and rendering the 400 without retrying — but be honest in the copy that a failed import changed nothing. This is a known backend gap; check whether it has been closed before building around it.
